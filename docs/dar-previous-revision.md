# PDF ฉบับเดิมและการยืนยันคืน/เลิกใช้

## พฤติกรรมที่เพิ่ม

- DAR ประเภทแก้ไขแยก PDF ฉบับใหม่และฉบับเดิม ชุดละ 1–20 ไฟล์ ไฟล์ละน้อยกว่า 25 MB
- เลือกใช้ต้นฉบับจาก Master List ที่ตรงกับรหัส/Rev. ได้ หรือปิดตัวเลือกนั้นแล้วแนบ PDF ฉบับเดิมจากเครื่อง พร้อมตรวจนามสกุล MIME และเนื้อหา PDF
- เซิร์ฟเวอร์เก็บสำเนาฉบับเดิมแยกไว้กับ DAR ก่อนส่งคำขอ ไฟล์นี้จึงไม่หายตามการเปลี่ยน/ยกเลิกต้นฉบับใน Master List และไม่ปนกับ PDF ฉบับใหม่ที่แจกจ่าย
- หน้า DCC เปิดดู/ดาวน์โหลดฉบับเดิมแยกจากฉบับใหม่ได้ เอกสารที่ยังไม่อนุมัติเมื่อลบ DAR จะลบไฟล์ทั้งสองชุด
- เมื่อแจกจ่าย Rev. ใหม่สำเร็จ ระบบสร้างรายการคืนสำหรับแผนกที่มีหลักฐานรับ Rev. เดิมจริง รวม QA/QC เป็นแผนกเดียว และไม่สร้างรายการซ้ำเมื่อเรียกซ้ำ
- หากแผนกนั้นได้รับจัดสรรฉบับใหม่ ต้องรับฉบับใหม่ก่อนยืนยันคืนฉบับเดิม แผนกที่เลิกใช้เอกสารและไม่ได้รับฉบับใหม่ยังยืนยันคืนได้
- ผู้รับยินยอมใช้ชื่อและลายเซ็นที่ลงทะเบียน ระบบเก็บภาพลายเซ็น ณ เวลายืนยัน วันที่ ผู้ยืนยัน และประวัติการทำรายการ
- ลายเซ็นคืนลงในช่องคืนของใบแจกจ่าย–เรียกคืนเดิม อ้างอิง DAR เดียวกัน ช่องรับคงใช้หลักฐานครั้งแรก ผู้มีเฉพาะหลักฐานคืนจะมีช่องรับว่าง
- DCC ดูสถานะ/ประวัติและกด “ตรวจรายการคืนฉบับเดิม” เพื่อประสานรายการที่ตกค้างได้ โดยไม่สร้างใบแจกจ่ายใหม่ ไม่สร้างรายการคืนใหม่ให้ Rev. ที่ถูกแทนที่ไปแล้ว
- การประสานรายการคืนที่ขัดข้องไม่ทำให้ PDF ที่แจกจ่ายสำเร็จถูกลบหรือเปลี่ยนเป็นแจกจ่ายล้มเหลว
- เมื่อยกเลิกแจกจ่าย รายการคืนที่ยังไม่ยืนยันถูกยกเลิกตาม หลักฐานที่ยืนยันแล้วเก็บไว้ หากมีหลักฐานคืนแล้วไม่อนุญาตลบใบแจกจ่ายถาวร
- DAR เดิมที่ไม่มีข้อมูลไฟล์ก่อนหน้ายังอ่านและแก้วันที่/เหตุผลได้ตามสิทธิ์เดิม เอกสารใหม่ใช้ขั้นตอนเดิม

ระบบไม่สามารถลบไฟล์ที่ดาวน์โหลดไว้ในเครื่องของผู้รับแทนผู้รับได้ ผู้รับต้องนำฉบับเดิมออกจากจุดใช้งานก่อนกดยืนยัน

## ติดตั้ง

GitHub Pages ติดตั้งหน้าเว็บอัตโนมัติเมื่อ push main ส่วน Cloud Functions และ Rules ต้องติดตั้งแยกใน Cloud Shell ของโครงการ:

```bash
cd ~/Document-Control-System01
git pull --ff-only
bash scripts/deploy-dar-returns.sh
```

ต้องให้คำสั่งรายงาน `Deploy complete!` ก่อนเริ่มใช้การส่ง DAR ประเภทแก้ไขเวอร์ชันใหม่นี้ สคริปต์ไม่แก้การแจ้งเตือน ประกาศ หรือระบบผู้ใช้ และเลือกติดตั้งเฉพาะฟังก์ชันที่เกี่ยวข้องกับ DAR/แจกจ่าย/คืนเอกสาร

ไม่มีการย้ายหรือลบข้อมูลจริงโดยสคริปต์นี้ หลังติดตั้งให้ทดสอบด้วย DAR ทดลองหนึ่งชุด: แนบฉบับใหม่/ฉบับเดิม → DCC อนุมัติ → แผนกเดิมรับฉบับใหม่ → ยืนยันคืน → DCC เปิดใบแจกจ่าย–เรียกคืนและตรวจลายเซ็นทั้งสองช่อง

## การตรวจสอบก่อนส่งโค้ด

- Build และ TypeScript: ผ่าน
- ทดสอบบริการสร้าง DAR: แยกไฟล์สองชุด, ตรวจ PDF เดิมก่อนอัปโหลด, ไม่บันทึก DAR หากสำรองไฟล์เดิมล้มเหลว
- ทดสอบ backend ด้วย PDF bytes จริง: เก็บครบหลายไฟล์, ต้นฉบับถูกลบแต่สำเนายังอยู่, ป้องกัน path ข้ามบัญชี/DAR, Rev. ไม่ตรง และไฟล์เสีย
- ทดสอบคืนเอกสาร: สิทธิ์แผนก/บัญชี active, consent, ชื่อ/ลายเซ็นจากโปรไฟล์, ลงชื่อซ้ำ, ยกเลิกระหว่างเซ็น, QA เดิม, แผนกที่ไม่รับฉบับใหม่, เปิดรายการคืนที่ยังไม่เซ็นใหม่หลังเริ่มแจกจ่ายใหม่
- Firebase Firestore Emulator: ผ่าน 24 assertions รวม query ที่ใช้จริง, ป้องกันเขียนหลักฐานเอง, ป้องกันแก้ snapshot, ป้องกันเลื่อนสิทธิ์, และคงสิทธิ์ DCC แก้วันที่/เหตุผล
- Chromium: ตรวจช่อง PDF อัตโนมัติ/แนบเองแยกกัน, consent/ข้อผิดพลาด/ลองใหม่/ประวัติ, ใบพิมพ์แบบเดิมและช่องรับว่างสำหรับผู้คืนอย่างเดียว, หน้าจอมือถือ
- ทดสอบซ้ำส่วนดาวน์โหลด PDF/ZIP, แจกจ่ายหลายไฟล์, ยกเลิกรายแผนก/ทั้งชุด และการแก้ DAR เดิม

การทดสอบนี้ใช้ข้อมูลจำลองและ Emulator ไม่ได้สร้าง DAR หรือเซ็นรับ/คืนแทนพนักงานในฐานข้อมูลจริง ต้องทดสอบกับบัญชีจริงหลังติดตั้ง Firebase

I've set up prototype Security Rules to keep the data in Firestore safe. They are designed to be secure for department-scoped reads and server-only return evidence, with immutable previous-revision snapshots. However, you should review and verify them before broadly sharing your app. If you'd like, I can help you harden these rules.
